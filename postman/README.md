# Vistona API audit and Postman guide

This audit reflects the current handlers under `src/app/api`. It describes implemented behavior, not planned features. There are 24 route files and 31 HTTP operations. Dashboard page access uses server-side session checks; APIs still enforce authorization independently.

## Real account workflow

Normal onboarding does not require the seeded demo accounts:

1. Visit `/signup` or send `POST /api/auth/signup` with `name`, `email`, `password`, `restaurantName`, and `city`. This endpoint always creates a new tenant, restaurant, and MANAGER account in one PostgreSQL transaction. It rejects role, tenant, and restaurant fields from the client, hashes the password, and starts a session.
2. The owner signs in at `/login` using `POST /api/auth/login`.
3. A manager creates waiter/kitchen accounts directly at `POST /api/staff`, or creates a single-use seven-day invite at `POST /api/staff/invite`; invited staff join at `/join` or `POST /api/auth/join`. The invite alone determines role and restaurant.
4. The manager uses `/manager/staff` for staff list/create/edit/deactivate. Each operation is scoped to the manager's authenticated tenant and restaurant.
5. Any signed-in user can use `/account` to view their account, update their name, change their password, and log out. Changing a password requires the current password and invalidates existing session versions.

The public `/signup` page intentionally does not offer a role selector. Public creation always makes a manager for a new tenant/restaurant; staff roles require manager creation or an invite. This prevents selecting MANAGER to join an existing restaurant.

## Setup

Use a local PostgreSQL database and configure `DATABASE_URL` and a random `JWT_SECRET` of at least 32 characters outside source control. For payment API calls, also configure `RAZORPAY_KEY_ID`, `RAZORPAY_KEY_SECRET`, and `RAZORPAY_WEBHOOK_SECRET` locally. Do not add these values to the collection.

From the repository root:

```sh
npm install
npm run db:generate
npm run db:migrate
npm run db:seed
npm run dev
```

`db:migrate` runs `prisma migrate deploy` and applies the initial, payment, auth/staff, table-management, and menu-management migrations in order. `db:seed` runs `tsx prisma/seed.ts`. The app is then at `http://localhost:3000`. The collection's `baseUrl` defaults to this address.

The seed password is `DEMO_PASSWORD`, defaulting to `demo123`. The seed hashes it with bcrypt before writing it. Accounts created by the seed:

| Email                   | Password source                     | Role    | Tenant / restaurant                   |
| ----------------------- | ----------------------------------- | ------- | ------------------------------------- |
| `manager@vistona.local` | `DEMO_PASSWORD` (default `demo123`) | MANAGER | Anndham tenant / Anndham Family Dhaba |
| `waiter@vistona.local`  | `DEMO_PASSWORD` (default `demo123`) | WAITER  | Anndham tenant / Anndham Family Dhaba |
| `kitchen@vistona.local` | `DEMO_PASSWORD` (default `demo123`) | KITCHEN | Anndham tenant / Anndham Family Dhaba |
| `milan@vistona.local`   | `DEMO_PASSWORD` (default `demo123`) | MANAGER | Milan tenant / Milan Restaurant       |

The seed uses `gen_random_uuid()` database defaults; tenant, restaurant, and user IDs are generated when the seed runs and are not fixed values in source. Login returns the user's actual `id`, `tenantId`, and `restaurantId`. The Milan user/table/menu are development fixtures for isolation checks, not an onboarding flow. No live database query was performed as part of this audit, so these are seed-defined credentials and identities, not a claim that a particular database has been seeded.

## API reference

All JSON bodies below must be sent as raw JSON with `Content-Type: application/json`. Auth means a valid `vistona_session` cookie. `401` means no valid session; `403` means the session role is disallowed. Database/provider failures may also surface as `503` on handlers that catch them, or `500` on payment handlers that do not.

An attempted status outside the current lifecycle can return `409` before a role-specific forbidden result. To test a role-based `403`, use an order in a state where the requested transition is otherwise valid.

## Session behavior

- Login does not return a bearer token. It returns the user identity and sets the signed `vistona_session` cookie with `HttpOnly`, `SameSite=Strict`, path `/`, and a 12-hour max age. `Secure` is enabled in production.
- Protected APIs read that cookie. Do not add `tenantId`, `restaurantId`, or role headers/body fields; the session is the source of identity.
- Postman stores and sends cookies in its cookie jar for the same host. Keep requests on `localhost` consistently; `127.0.0.1` is a different cookie host. No manual `Authorization` header is required.
- Logout expires the browser cookie. Sessions remain signed HMAC cookies, but each protected request now rechecks the active user and `authVersion` in PostgreSQL. Password change, staff deactivation, and staff role changes invalidate earlier tokens. Logout itself clears the caller's cookie; a copied token is otherwise valid until expiry unless its account version changes.
- Login as another role overwrites the cookie for the same host. For a clean beginner workflow, run Logout between logins. No separate browser or manual token switch is needed.

## Postman run order

Import `Vistona-API.postman_collection.json`. The collection generates unique local test accounts and uses strong non-production passwords. Run requests in this order:

1. Run `01 Authentication / Create Manager and Restaurant`. It creates a unique owner and starts a manager session; `02 Manager / Get restaurant` captures the restaurant slug and IDs.
2. In `03 Staff Management`, run list, create waiter, create kitchen, and invite requests. `Manager cannot create another Manager as staff` must return `400`.
3. In `11 Tables`, create the test table first; the collection stores its database ID and QR token. In `10 Menu`, create a dish and run edit/stock tests. Leave the test dish active/in stock until waiter and QR ordering tests finish. New restaurants start with no tables or dishes.
4. Run Logout, then Login Waiter from `01 Authentication`. In `04 Waiter`, verify allowed reads/table changes and manager/kitchen denials; create an order before kitchen tests.
5. Run Logout, then Login Kitchen. In `05 Kitchen`, transition the waiter order through PREPARING and READY, then test manager/waiter API denials.
6. Run `06 Account` while signed in as the account being tested. Password change signs out current sessions; use Login again with the updated password variable afterward.
7. Run `07 Authorization Tests` after Logout; both requests expect `401`. Then run `13 Security and Tenant Tests` while logged into the Anndham manager account for cross-tenant ID attempts. The optional Milan fixture requests still require the development seed and a `milanPassword` matching its `DEMO_PASSWORD`.
8. Run `08 QR Ordering` with the table token created in `11 Tables`; the menu response includes the resolved table and out-of-stock flags. QR requests create real orders. Payment creation contacts Razorpay and requires local test credentials; invalid signature requests only test rejection.
9. The final staff deactivation request in `13 Security and Tenant Tests` confirms the disabled waiter can no longer log in. The invite join request changes Postman's cookie to the invited account, so log in as the manager again before manager-only requests.

The collection's `12 KOT` folder is intentionally documentation-only because no KOT endpoint exists. The collection does not invent one.

## Tenant isolation and findings

Core authenticated restaurant/table/menu/order queries derive `tenantId` and `restaurantId` from the signed-in session, and updates include those scope values in SQL. QR requests resolve the restaurant by its public slug and scope menu/table/order operations to that restaurant. A client-supplied tenant or restaurant ID is not used as authority by those handlers.

Important payment security gap: `POST /api/payments/create-order` accepts any database `orderId` and has no session or tenant ownership check. The payment record also relates to `Order` by order ID only. The checkout signature and webhook HMAC protect marking a payment paid, but they do not authorize who may create/retrieve a provider order. Treat this endpoint as a backend security issue; Postman tests document the existing behavior rather than masking it.

There is no middleware/proxy protecting dashboard page routes in this repository; API handlers enforce their own session/role checks. The browser UI is not the security boundary.

The login handler returns `400` before querying the database when JSON parsing or the email/password schema fails; wrong credentials return `401`, and missing database/JWT configuration or query errors return `503`. In Postman use Body > raw > JSON, `Content-Type: application/json`, and exactly this shape:

```json
{
  "email": "manager@vistona.local",
  "password": "demo123"
}
```

If that exact valid body still gives `400`, check for extra quote characters, trailing commas inside values, or omitted `password`; if it gives `401`, the seeded password may differ from the current `DEMO_PASSWORD` or the seed may not have run.
